Arquitetura com Claude Code + Redis (NoSQL com TTL nativo)
O Redis é ideal para esse caso por oferecer TTL nativo por chave — os dados literalmente expiram e somem sozinhos.

Por que Redis?
TTL automático: EXPIRE ou SET key value EX 86400 já resolve

Estrutura simples: cada lead não lido é um registro com expiração configurável

Contagem instantânea: comandos como SCARD (se usar sets) ou GET + increment são atômicos

Sem manutenção: zero queries de limpeza, zero cron jobs de faxina

Setup mínimo: docker run redis ou Redis Cloud grátis

Estrutura de dados
text
# Conversas não lidas controladas por TTL
chave: unread:{phone}
valor: timestamp da última mensagem
expira: 2 horas (ajustável) após a última mensagem

# Contagem rápida
chave: unread_count
valor: número inteiro atual

# Controle de estado (anti-flood de alertas)
chave: alert_sent
valor: "true" ou "false"
expira: 30 minutos

Implementação com Claude Code
Dois scripts Python simples, agendados separadamente:

Script 1 — webhook_listener.py
Deixa rodando (Flask/FastAPI simples) e apenas escuta o WhatsApp:

python
from flask import Flask, request
import redis
from datetime import datetime

app = Flask(__name__)
r = redis.Redis(host='localhost', port=6379, decode_responses=True)

TTL_SEGUNDOS = 7200  # 2 horas — ajuste conforme seu SLA

@app.route('/whatsapp', methods=['POST'])
def receber_whatsapp():
    data = request.json
    phone = data['entry'][0]['changes'][0]['value']['messages'][0]['from']
    
    chave = f"unread:{phone}"
    r.set(chave, datetime.now().isoformat())
    r.expire(chave, TTL_SEGUNDOS)  # renova TTL a cada nova mensagem
    
    return '', 200
Comportamento: cada mensagem novo zera o TTL. Se o lead ficar 2h sem mensagem nova e ninguém marcou como respondido, o registro expira e some da contagem automaticamente.

Script 2 — comparator.py
Executado via cron a cada 15 minutos e uma variante diária às 18h:

python
import redis
import requests
import os

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

# Conta leads não lidos
unread_chaves = r.keys("unread:*")
unread_count = len(unread_chaves)

# Consulta CRM
crm_resp = requests.get(
    "https://api.liguetalk.com/v1/leads/count",
    headers={"Authorization": f"Bearer {os.getenv('LIGUETALK_TOKEN')}"}
)
crm_count = crm_resp.json()['count']

# Compara
if unread_count != crm_count:
    ja_enviei = r.exists("alert_sent")
    if not ja_enviei:
        enviar_alerta(unread_count, crm_count)
        r.setex("alert_sent", 1800, "true")  # não repete por 30 min
else:
    r.delete("alert_sent")  # voltou ao normal, reseta flag

def enviar_alerta(unread, crm):
    webhook_url = os.getenv('ALERT_WEBHOOK_URL')
    requests.post(webhook_url, json={
        "text": f"atenção: leads diferentes entre o whatsapp e Liguetalk. WhatsApp: {unread}, CRM: {crm}"
    })

2. Set — ✅ confirmado, vamos adotar
Você confirmou o uso de Set + Hash no lugar de KEYS unread:*. Isso elimina o problema de performance com KEYS e escala melhor. A estrutura fica assim:

python
# webhook_listener.py — ao receber nova mensagem
r.sadd("unread_active", phone)                # adiciona ao set de ativos
r.hset(f"lead:{phone}", "last_msg", timestamp) # armazena metadados
r.expire(f"lead:{phone}", TTL_SEGUNDOS)        # TTL na hash individual

# comparator.py — contagem rápida via SCARD
unread_count = r.scard("unread_active")

4. Persistência do Redis — ✅ ok, com ressalvas
A preocupação com serviço de terceiro é justa. Como o Redis é local, o risco principal é perder os dados ao reiniciar o container. Isso pode gerar alertas falsos (contagem zera e dispara notificação).

Recomendação: habilite AOF (Append Only File) no Redis. É uma linha de configuração:

text
# redis.conf
appendonly yes
Ou no Docker:

bash
docker run -d --name redis -p 6379:6379 redis redis-server --appendonly yes
Isso garante que, se o container reiniciar, os dados das conversas ativas não serão perdidos.

docker run -d --name redis -p 6379:6379 redis redis-server --appendonly yes

Scalability

Using Set SCARD eliminates the O(N) KEYS command.

The 'leads' set can hold thousands of entries; membership check is O(1).

As volume grows, ensure the sync job (sync_leads_from_crm) is efficient
(e.g. fetch all phones with a single request).

For very high volumes, consider Redis Cluster or sentinel for HA, but
the single‑instance design is sufficient for most lead monitoring use cases.

Summary
This architecture delivers a self‑cleaning, low‑maintenance solution to detect
discrepancies between WhatsApp unread leads and CRM counts.
Redis TTL handles expiration automatically.
A dynamic 'leads' set (synced from the CRM) filters out non‑lead contacts.
Monitoring runs every 15 minutes, with intelligent anti‑flood alerting.
The removal of the daily summary simplifies the system and avoids false alerts
due to API latency.
All components are simple Python scripts and a single Redis container.
